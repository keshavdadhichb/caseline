Agentic AML detection · hackathon build

A query-driven agent for suspicious-activity detection

Ask Caseline a question in plain English. It parses intent, builds a dynamic execution plan naming which detection tools it will run and which it is skipping and why, then returns risk-scored, explained case files with a drafted Suspicious Activity Report. Every number on screen comes from a live endpoint — nothing is hardcoded or invented.

> Is customer ID 4521 suspicious?
→ scoped to 4521, ran typology rules + anomaly scoring + network analysis
→ HIGH risk, score 1.00: STRUCTURING_HIGH, RAPID_MOVEMENT, FAN_IN_RING
→ 10-node ring, $254,317 gathered from 9 accounts, 85% moved out in 48h
→ recommended action: report · SAR narrative drafted (239 words)
200,029 transactions · 150,971 accounts model: IsolationForest (seed 42) typologies: 7 tests: 157 · evals: 12/12 · e2e: 45/45

02 · Capability matrix

What runs without each key

One key is load-bearing, one is a strictly optional presentation layer. Nothing silently fails — every gap below degrades to a stated, deterministic fallback.

ANTHROPIC_API_KEY Required
Query planning & SAR draftingthe only two places an LLM touches the pipeline
Rules, anomaly model, graph analysis, risk scoring100% deterministic Python — zero dependency on this key, with or without it
The 3 canonical demo queriespre-warmed in .cache/plans, replay instantly and byte-identical
Novel, never-seen queriesdegrades to a plain “could not be planned” reply instead of running a meaningless full-dataset sweep
SAR narrativesfalls back to a deterministic template built only from facts already in the case file — never ships empty
GEMINI_API_KEY Optional
Presentation layer onlynever plans a query, never drafts a SAR, never sees a score it could influence — enforced: this key is imported nowhere in agent/ or any detection tool
Everything above the linedetection, planning, SAR, PDF export, evals — entirely unaffected either way
“Explain simply”falls back to a real plain-language summary built from the case’s own evidence, just without the model-written prose
Read aloudfalls back to the browser’s own built-in speech synthesis — still works, no key, no network
Illustration & voice inputno fallback exists — the image simply doesn’t render and the mic button doesn’t appear

06 · Detection

Seven typologies

Each a deterministic rule or graph check with its own domain rationale — see backend/tools/rules_engine.py and graph_analysis.py, or ask Caseline itself ("What is structuring?") for the same explanations rendered live.

Structuring
confirmed
≥5 deposits, $9,500–$10,000
within 7 days, AND ≥60% out
within 7 days
The onward transfer separates laundering from an ordinary cash business — a shop banks its takings and leaves them; a mule gathers and forwards.
Structuring
indicator
≥3 txns, $9,000–$10,000
within 7 days, either side
A weaker signal alone — plenty of legitimate businesses look like this — so it surfaces an account for review but never escalates it by itself.
Velocity
peak txns/hour >4σ above
own baseline, 10+ prior txns
Compared against the account's own history, not the population — the 10-transaction minimum exists because a standard deviation from 3 transactions is noise.
Rapid movement
≥80% inbound out within 48h,
$1,000+ from 2+ senders
Requiring 2+ senders is what distinguishes a funnel from ordinary two-party settlement, where fast in-and-out is normal.
High-risk amount
one txn >4σ above own
history, 10+ prior txns
Same self-comparison reasoning as velocity — the account is measured against itself, never the population.
Fan-in ring
≥5 distinct senders within
7 days, ≥60% moving onward
Found on the transaction graph, not any single account's numbers — corroborates the rules rather than repeating them.
Round-trip cycle
closed loop, 3–5 hops
on the transfer graph
Two-party back-and-forth is deliberately excluded — that's just two people paying each other, extremely common and not laundering.
risk_score (ranking only) = 0.45 × rules_component + 0.35 × graph_component + 0.20 × anomaly_component risk_level (tier) = HIGH if a STRONG rule fired AND corroborated by a second detection method (graph or anomaly-high); MEDIUM if exactly one method fired (or only a weak rule); LOW if anomaly-high alone
07 · Verification

Testing & evals

make test-live
# 45 end-to-end checks through the frontend's own path
make verify
# the 12-query eval suite + regenerates the baseline table above
make eval

157 tests total. make eval regenerates data/method_metrics.json from scratch on the held-out split, so the numbers above and the app's own Method panel are always exactly what was last measured, never hand-typed. TESTING.md has the full report. QUERY_AUDIT.md is a 20-query manual audit with every response captured verbatim — including five open quality findings not yet resolved. Read it before assuming everything below "the tests pass" is settled.

08 · Data

Dataset & disclosure

IBM Transactions for Anti-Money Laundering (HI-Small)

Via Kaggle, Community Data License Agreement — Sharing 1.0. ~200k rows sampled from 5.08M raw transactions with a fixed seed, preserving every labeled laundering transaction and its counterparties. Full sampling methodology, the laundering_type join and its known ~62% coverage gap (a property of the upstream Kaggle files, not a join bug), currency normalization, and the customer-4521 alias are documented in DATA.md.

One synthetic ring, clearly marked

laundering_type = "SMURFING (synthetic)", transaction ids S0000…. 9 mule accounts each make 3 sub-threshold deposits into aggregator account 4521 over 6 days, which then moves ~85% of the pooled funds out within 48 hours. This is the deliberately narratable catch used throughout this page and the live demo.

AI tooling

Built with Claude Code (Anthropic). Anthropic API (claude-sonnet-4-6) for query planning and SAR drafting — the only two places an LLM touches the pipeline. Google Gemini API, presentation layer only, entirely optional — see the capability matrix above.

All detection logic is deterministic Python (pandas / scikit-learn / networkx). No LLM computes, adjusts, or ranks a risk score.
